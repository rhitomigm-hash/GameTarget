# PLATEAU 重ね合わせ検証(第0段階)

PLATEAU(3D都市モデル)の建築物を、既存の `prototype/terrain.js` の地形に
**位置ずれなく重ねられるか**だけを確かめる検証ページ。ゲーム本体には一切影響しない。

> **第1段階に進んだため、読み込み処理は `prototype/plateau.js` に移設した**
> (`terrain.js` と同じく本体の部品)。このページはそれを import して使う計測用の窓口。
> 本体で試すなら `prototype/?city=1`(LOD1)/ `?city=2`(LOD2)。
>
> このページは市区町村コードを決め打ちするが、本体は全国版(`all-bldg-...`)を使い、
> 基準点の座標から自動でその市区町村を引き当てる。

検討の背景は `tmp/PLATEAU検討メモ.md`(非公開・リポジトリには含まれない)にある。

## 動かし方

```
python -m http.server 8000 --directory c:\Claude\game
```
→ http://localhost:8000/experiments/plateau/

URL パラメータ:

| パラメータ | 既定 | 意味 |
|---|---|---|
| `city` | `13101` | 5桁市区町村コード。`13101`千代田 / `13104`新宿 / `14100`横浜 / `27100`大阪 |
| `lon` `lat` | プリセット | 基準点(地形と建物の共通原点) |
| `r` | `2500` | この距離内の建物タイルを読む(m) |
| `lod` | `1` | `1` = 箱のみ(テクスチャ無し) / `2` = 写真テクスチャ付き |
| `n` | LOD1:`4` LOD2:`40` | 読み込むタイル数の上限(負荷の保険) |

プリセット4地点はすべて LOD1・LOD2 両方の配信があることを確認済み。

## 何を見るか

1. **建物が地面に正しく接しているか。** 埋まる/浮くなら高さ基準の補正がずれている
2. **「高さ基準の補正」の自動推定値。** ばらつき(四分位範囲)が小さければ推定は信用できる
3. **通信量の削減率。** Range で glTF だけ取る効果
4. **fps と頂点数。** 熱気球の飛行に耐えるか

## 実データで確認済みの前提(2026-08-27)

配信サービスに実際にアクセスして確かめた。仕様書の記述ではなく実測。

| 項目 | 結果 |
|---|---|
| エンドポイント | `https://api.plateauview.mlit.go.jp/datacatalog/3dtiles/<5桁市区町村コード>-bldg-lod1-latest/tileset.json` |
| 認証 | 不要 |
| CORS | `access-control-allow-origin: *`。ブラウザから直接読める |
| Range リクエスト | `Accept-Ranges: bytes`、206 が返る(クロスオリジンでも可) |
| 建物の MVT 配信 | **存在しない**(404)。MVT は `luse` `fld` 等のみ。建物は 3D Tiles 一択 |

### 設計に影響した3つの発見

1. **b3dm の約76%は使わない属性テキストだった。**
   千代田区の末端タイル `data0.b3dm` は 13.5MB。内訳は batchTable JSON 10.2MB、
   属性バイナリ 0.15MB、**glTF 本体はわずか 3.0MB**。
   glTF はファイル末尾にあるので、先頭28バイトのヘッダを Range で読んでオフセットを求め、
   glTF 部分だけを Range で取れば **76%削減**できる。`plateau.js` の `fetchGlb()` がこれ。

2. **ジオメトリは Draco 圧縮**(`KHR_draco_mesh_compression`)。
   `DRACOLoader` が必要。デコーダは jsDelivr の three 同梱版を使うのでビルド工程は不要のまま。

3. **座標は `CESIUM_RTC`**(中心からの相対値)。
   Three.js の `GLTFLoader` はこの拡張を無視するため、glb の JSON チャンクから
   自前で中心座標を読んで足す必要がある。放置すると建物が地球の中心に置かれる。

### テクスチャは LOD2 にしかない(2026-08-27 確認)

**LOD1 は仕様上テクスチャを持たない。**マテリアルに `baseColorTexture` が無く、
高さだけの箱なので、写真を貼りたければ LOD2 を使うしかない。

LOD2 の b3dm には `EXT_texture_webp` で **タイルごとにアトラス1枚**の WebP が入っている
(three の `GLTFLoader` が対応済み。追加のローダは不要)。
`COLOR_0`(頂点色)を持つメッシュもあり、テクスチャの無い面はそちらで着色されている。

千代田区での比較(実測):

| | LOD1 | LOD2(テクスチャ付き) |
|---|---|---|
| 末端タイル数 | 約20枚 | **463枚** |
| 1枚のサイズ | 12.9 MB | **0.14〜1.09 MB** |
| 1枚の建物数 | 1,846棟 | 75棟 |
| batchTable の割合 | 76% | 38%(それでも Range は効く) |

**タイルの粒が細かいのは飛行シムにとって有利。**気球の周囲だけを読む方式と相性がよく、
LOD1 のように「1枚読むだけで12.9MB」にならない。半径で絞る前提なら LOD2 のほうが軽くなりうる。

> 注意: マテリアルを無条件に上書きするとテクスチャが消える。
> `loadBuildings` は `material.map` を持つメッシュには手を触れず、
> 持たないものだけ単色に差し替えている。

### タイルツリーの形(千代田区 LOD1)

`refine: REPLACE` の2〜3階層。**上位タイルは軽く、末端タイルだけが重い**。

| 階層 | サイズ | 中身 |
|---|---|---|
| ルート | 0.16 MB | 大きい建物 20棟だけ |
| 中間 | 0.19 MB | 同上(粗い) |
| 末端 | 12.9 MB | 1,846棟(実質すべて) |

飛行シムでは「遠景は上位タイル、直下だけ末端タイル」という使い分けが効きそうだが、
REPLACE なので同時に出すと重複する。第1段階以降の課題。

### 高さ基準のずれ

PLATEAU の高さは**楕円体高**、地理院DEMは**標高**。日本ではおよそ 30〜40m ずれる。
千代田区タイルの `boundingVolume.region` の下端が 33.5m だったこと(地表の標高は数m)から、
ずれが実在することは確認済み。**実測値はこのページで測る。**

推定方法(`estimateGeoidOffset`): 建物は地面に建っているという前提で、
100m 格子ごとに最も低い頂点を「その場所の地面の楕円体高」とみなし、
地理院DEMの標高との差の中央値をとる。中央値なので一部の外れ値には引きずられない。

## 結果

### ✅ 建物は地面に接した(2026-08-27 目視確認)

**第0段階の本題は達成。**PLATEAU の建物を地理院DEMの地形に、位置ずれなく重ねられた。
これで以下が実地に成立したことになる:

- ECEF → ローカル ENU 座標(x:東+, y:上+, z:南+)の変換と軸の向き
- `CESIUM_RTC` の中心座標を自前で足す処理
- Draco 圧縮ジオメトリの読み込み
- Range で glTF 部分だけを取る節約
- 楕円体高 → 標高の補正(`estimateGeoidOffset` による自動推定)

**技術的な障害は無くなった。**以降は「重ねられるか」ではなく
「どう遊びに使うか」と「どこまで負荷に耐えるか」の問題になる。
